# C2 — RAG 基礎（切塊／向量／檢索／組裝／評估召回）

> 時長：1 hr　|　投影片：`class-02-…pptx`（核可後產）　|　Lab：`lab-02.md`
> 交付：自建一條 RAG 鏈（切塊→embedding→向量庫→檢索→組 prompt→answer），能用召回率自评測。

---

## 1. 這堂要解決什麼

C1 把 LLM 鎖成「**可控的生成器**」，但它只有「**你餵給它的**」知識。
兩類問題 prompt 救不了：
- **私域資料**（公司文件、產品手冊）——LLM 訓練時沒見過。
- **最新資訊**（價格、庫存、政策）——訓練 cutoff 之後。

**解法＝RAG（Retrieval-Augmented Generation）**：先去「**檢索**」相關片段，再把片段「**塞回**」prompt 讓 LLM 生成。

> **心智模型**：RAG＝**開放書考**——允許翻書（向量庫=書），但答案要自己寫（LLM=考生）。
> 純 prompt 是**閉卷考**（只靠腦子）；RAG 是開卷，**成績取決於「翻到對的書頁」**。

**驗收口**：一條能跑通的 RAG 鏈＋對 ≥10 段資料的召回截圖。

## 2. 全流程圖（本卡地圖）

```
文件 → [切塊] → [embedding] → [存向量庫]
                                    │
問題 → [embedding] → [相似度檢索 top-k] → [組 prompt（片段+問題）] → LLM → answer
```

五個關鍵決策點：**切塊多大、哪個 embedding、向量庫用誰、top-k 取幾、prompt 怎麼組**。本卡逐一拆。

## 3. 切塊策略（chunking）

### 3.1 chunk size 與 overlap

| 參數 | 太小（如 100 char） | 太大（如 4000 char） | 建議 |
|------|---------------------|----------------------|------|
| **檢索精度** | 片段太碎，缺上下文 | 太長，雜訊多、相關度被稀釋 | **200–800 token** 看文件類型 |
| **成本** | 塊數多，embedding 多 | 塊數少 | 中 |
| **召回品質** | 可能只命中一兩句 | 命中一整段（含雜訊） | 取中＋加 overlap |

- **overlap**：相鄰塊重疊 10–20%，避免「答案正好斷在兩塊之間」。
- **語義切塊**（比「固定長度」更好）：依**段落／小標**切，而非按字數硬切——語義完整塊檢索更準。

> **心智模型**：chunk＝**圖書館的書頁**。切太碎＝把一段話撕成碎片（查得到字組不成句）；切太大＝整本書塞一頁（翻到那頁要讀半小時）。目標＝**一页講一件事**。

### 3.2 三種切法對照

| 切法 | 原理 | 優 | 劣 |
|------|------|----|----|
| 固定長度 | 每 N 字切一刀 | 簡單 | 常切碎语义 |
| 依結構 | 依 markdown 標/段落切 | 語義完整 | 需懂文件格式 |
| 語義（embedding 相似度斷點） | 在語義跳躍處切 | 最優 | 貴、複雜 |

> 生產建議：**先依結構切**（最划算）；效果不夠再上語義切塊。

## 4. Embedding 模型選擇

embedding 是把「文字」變成「向量」（數字陣列），讓「意思相近」的向量在空間裡距離近。

| 模型 | 維度 | 相對成本 | 適用 |
|------|------|----------|------|
| **`text-embedding-3-small`**（OpenAI） | 1536 | 低 | **課程主用**、跨語言尚可 |
| `text-embedding-3-large` | 3072 | 中（約 2 倍） | 召回要求高、C5 對比 |
| BGE-m3（本地） | 1024 | 0（自架） | 內網/多語/長文 |

> **心智模型**：embedding 是「**把意思翻成坐標**」——選 embedding 就像選「**哪套坐標系**」，坐標系不同，同一句話的位置不同，**比較才有意義**。
> 注意：**檢索與儲存要同一套 embedding**（不能存 A 套、查 B 套）。

---

## 5. 向量庫（本課用 Chroma）

| 向量庫 | 型態 | 適用 |
|--------|------|------|
| **Chroma**（`chromadb`） | 純 Python、`.chroma` 本地目錄、無 server | **課程主用**、原型、小量 |
| PgVector | Postgres 擴充 | 生產、已用 PG |
| Qdrant / Milvus / Pinecone | 獨立 service / SaaS | 大量、多租、要 HA |

> **心智模型**：向量庫＝「**以意搜書的圖書館**」。Chroma 是**桌上型**（簡單、够用），PgVector 是「**把書放進你現有的檔案室**」，Qdrant/Milvus 是「**専門的中央圖書館**」。選法：**先簡單（Chroma），量大了再遷**。

## 6. 組 prompt：檢索結果怎麼回灌

**關鍵**：把 top-k 檢索片段**明確標註**塞進 prompt，並要求 LLM「**只依據這些資料回答**」（減少幻覺）：

```
system: 你是知識庫問答器。只能依據【資料】回答；資料沒有就說「我不確定」。
user:
【資料】
<片段1>...</片段1>
<片段2>...</片段2>
【問題】
{question}
```

> **心智模型**：檢索片段＝**參考書**，prompt 是「**告訴 LLM 只準翻這几页**」。
> 沒有限制 → LLM 拿自己的（可能過期的）知識補，＝幻覺。

## 7. 評估召回（Recall / Faithfulness）

RAG 的「**好**」拆成兩件事，分別測：

| 指標 | 問什麼 | 怎麼量 |
|------|--------|--------|
| **Recall（召回）** | 相關片段有没有被檢索到？ | 標準答案所在塊**有沒有進 top-k**（k=3/5） |
| **Faithfulness（忠實）** | answer 有沒有胡說（超出片段）？ | 人核/LLM 評：answer 每句能否被片段支撐 |

**常見 RAG 失敗模式**：
1. 檢索不到（切塊/embedding 選錯）→ Recall 低。
2. 檢索到了但 prompt 沒用好 → Faithfulness 低。
3. top-k 太小漏、太大稀釋 → 兩者皆中。
4. 文件太長沒切好 → 關鍵句被切散。

> **心智模型**：RAG 品質＝**檢索分 × 生成分**（乘法，不是加法）。
> 檢索 0 分→再好的 LLM 也是 0；生成 0 分→再準的檢索也白費。**分開測才知道哪半要修**。
