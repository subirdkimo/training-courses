> 交付：把 C2–C5 的組件**拼成端到端的完整應用**，可被內部使用者呼叫；產出 1 頁**交付報告**＝結案。

---

## 1. 這堂要解決什麼

C2–C5 各做了一個「**好零件**」：RAG 檢索、Tool 閉環、Agent 迴路、評測三軸。
但「零件好」≠「**應用能交付**」。本卡做最後一步：**組裝 + 硬化 + 上線 + 交付**。

交付物要能回答三件事（**任何人**看得懂、**任何時**都測得到）：
1. **它能幹嘛**（架構＋使用方式）。
2. **它跑得好不好**（C5 三軸分數＋成本）。
3. **壞了誰知道、怎麼修**（監控＋錯誤處理）。

> **心智模型**：**整合上線＝把「demo」變成「產品」。**
> Demo 是「在我本機、我環境、我資料下能跑」；產品是「**在別人手上、任意流量、故障狀況**下還可靠」。
> 兩者的差距＝**API 層＋key 管理＋錯誤/降級＋監控＋日誌**——本卡逐一補。

**驗收口**：一個可從外部呼叫的完整應用＋1 頁交付報告（架構圖/成本/latency/下一步）。

---

## 2. 端到端架構（拼在一起長什麼樣）

```
使用者请求
   │
   ▼
[API 層]  解析/驗證 + auth（key）          ← C6 新增
   │  (決定走哪條路：簡單問題直接答 / 需查資料走 RAG / 需執行走 Tool / 多步走 Agent)
   ├────────────► [RAG]      C2 檢索+組prompt
   ├────────────► [Tool]     C3 function calling
   └────────────► [Agent]    C4 ReAct 迴路（內部可再用 RAG/Tool）
   │
   ▼
[LLM 生成]  C1 結構化/自然語言
   │
   ▼
[回應]  + 埋點（成本/latency/錯誤）        ← C5 監控
```

**routing（分流）是整合的核心**：不是所有請求都走 Agent（貴/慢）——
**簡單請求走輕路徑**（直接 LLM / 單次 RAG），**才把複雜的交給 Agent**（C4 §6 鐵軌 + 自駕）。

> **心智模型**：**整合的第一課＝「分流」。**
> 把 90% 簡單請求導去最快最便宜的路徑，只用 10% 複雜請求動用 Agent——**成本與延遲都靠分流降下來**，不是靠「換更強模型」。

## 3. API 層（讓別人能呼叫）

把「本機 script」升級成「**可被呼叫的 API**」（本課用 FastAPI 範例，概念同理於 Express）：

```python
from fastapi import FastAPI, HTTPException
app = FastAPI()

@app.post("/ask")
def ask(req: Ask):            # Pydantic model 驗證輸入
    try:
        answer = pipeline(req.text)   # 你的整合 pipeline（C2-5 組件）
        return {"answer": answer, "meta": usage}
    except BudgetExceeded:
        raise HTTPException(503, "成本超限，請稍後重試")
    except Exception as e:
        raise HTTPException(500, "internal error")   # 不外洩內部細節
```

**API 層要處理的 4 件事**：
| 事 | 說明 |
|----|------|
| **輸入驗證** | Pydantic/schema 校驗，非法輸入不進管道（別讓爛 input 打到 LLM） |
| **auth** | 每個使用者/key 獨立計費＋限流（rate limit） |
| **錯誤映射** | 內部異常→乾淨的 4xx/5xx，**不洩密**（key、stack trace） |
| **降級（fallback）** | 主路徑失敗→備路徑（見 §4） |

---

## 4. key 管理 + 錯誤與降級（產品級硬化）

### 4.1 key 管理（產品級）
- **集中管理**：不在各 service 散落；用 secret manager / env，**永不進 git**。
- **獨立 quota**：每個 endpoint/環境**獨立 key＋預算上限**（C0 的 budget cap 在此落地）。
- **可單獨 revoke**：洩露/異常時能**只關一條**，不用全停。

### 4.2 錯誤處理 + 降級
| 故障 | 降級策略 |
|------|----------|
| LLM API 超时/5xx | 備用模型/provider 接手（**failover**）；仍不行→回「系統繁忙」 |
| 成本超預算 | 切**更便宜模型**跑簡單請求（**graceful degrade**），擋高成本 Agent |
| RAG 向量庫掛 | 退回「**只靠 LLM + 明確告知無資料**」，不硬答（**降級 honesty**） |
| Agent 超步數 | 回「已完成的部分」＋標註「未完成」（**部分交付**） |

> **心智模型**：**產品級＝「任何零件壞了，整體還能給一個『可接受』的結果」。**
> Demo 可以 crash，產品要**优雅降級**——使用者寧要「慢一點的舊答案」，不要「白屏/報錯」。
> **降級是設計出來的，不是出事了才想**（C4 失控案例在此收口）。

## 5. 日誌與可觀測性（壞了誰知道）

- **結構化日誌**（JSON）：每筆請求帶 `request_id / 走了哪條路 / tokens / latency / 成本`。
- **trace**：Agent 多步每步（Thought/Action/Observation）都記——**出事能重放**。
- **儀表板**（C5 指標的視覺化）：分數/成本/latency/錯誤率的即時曲線。

> **心智模型**：**日誌＝AI 應用的「行车記錄儀」。**
> 沒有它，線上問題只能「重現＋猜」；有了它，能「重放＋定位」——**這是 demo 和產品最隱形但最關鍵的差距**。

## 6. 交付報告（1 頁，結案標準）

**這 1 頁要讓「不看課程的人」也能理解並使用**——結構：

| 區塊 | 內容 |
|------|------|
| **能做什麼** | 一句話＋3 個範例請求/回應 |
| **架構** | 1 張圖（哪個請求走 RAG/Tool/Agent） |
| **品質** | C5 三軸分數（分數/成本/latency p95） |
| **成本** | 月預估成本＋預算上限設定 |
| **可靠性** | 降級策略＋監控指標清單 |
| **怎麼用** | API endpoint＋curl 範例＋key 從哪來 |
| **已知限制** | 不支援什麼／什麼情況會答錯 |
| **下一步** | 下一步建議（擴量/加功能/改模型） |

> **心智模型**：**交付報告＝「把工程決策變成別人能接手的文件」。**
> **寫得出這 1 頁＝你真的懂了**（寫不出「為什麼走這條路」＝只在跑 demo）；寫得出＝你已能獨立交付。

## 7. 30 天獨立驗收基準（結案口）

課程結束後 **30 天內**，學員獨立完成一個**新主題**（非課程案例）的同樣交付：
- **選型**＋**prompt**＋**RAG**＋**Tool**＋**Agent**＋**評測**＋**上線**全鏈。
- 交一份**同結構**的交付報告。
- **能答出**：「為什麼這條路走 RAG、那條走 Agent？」（分流理由）。

> **心智模型**：**結案不是「把課程案例做起來」，而是「換個主題還能照做」。**
> 能遷移到新領域＝**內化了方法**；只能照課程案例＝**背下來**。驗收抓的是前者。
