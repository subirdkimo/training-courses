# C5 — 評測與監控（回歸集 / 分數 / 成本 / latency 三軸）

> 時長：1 hr　|　投影片：`class-05-...pptx`（核可後產）　|　Lab：`lab-05.md`
> 交付：建一組 **≥20 案例回歸集**，對 RAG/Tool/Agent 跑**分數＋成本＋latency** 三軸，並設定線上監控埋點。

---

## 1. 這堂要解決什麼

C0–C4 都做了「**能跑**」的東西；但「能跑」≠「好用」，更≠「**改一改就變好還是變壞**」。
AI 應用最大的工程痛：**改動難量化**。你改了 prompt、換了模型、調了 chunk size——
- 「感覺比較好了？」 → 這是**信仰**，不是工程。
- 上線後「latency 變 3 倍成本翻倍？」 → 沒有埋點就**事後才驚覺**。

**本卡目標**：把「好不好用」變成**可重跑、可比較、可上線監視**的數字。

> **心智模型**：**評測＝AI 應用版的 CI（continuous integration）。**
> 傳統 code 有 unit test＋CI 才知道改動有沒有 regression；AI 應用也要有自己的「測試集＋打分＋監視」，
> **沒有它，每次改動都是擲骰子**。

**驗收口**：≥20 案例回歸集＋對兩個變體（A/B）打出「分數/成本/latency」三軸分數表。

---

## 2. 回歸集設計（≥20 案例）

回歸集＝**一組「輸入＋期望」**的案例，每次改動都重跑。

| 欄位 | 說明 | 例 |
|------|------|-----|
| `id` | 案例編號 | `c01` |
| `input` | 給 LLM 的輸入（問題/訂單/目標） | 「我上週三訂了一箱 A4 紙」 |
| `expected` | **期望的輸出結構/關鍵事實** | `{product:"A4紙",qty:1}` 或「提到 5 號」 |
| `assert` | 自動判定的規則 | `product == "A4 紙"` |
| `tag` | 分類（抽取/RAG/tool/agent） | `rag` |

**設計原則**：
- **夠多**（≥20）：少到極致容易被單例帶偏；**分布要覆蓋**常見＋**邊界**情況。
- **含邊界/負例**：空輸入、矛盾問題、超出知識——**負例最能暴露問題**。
- **可自動判定**：能用 `assert` 自動判分的**優先**（可重跑），純人核的作輔助。
- **穩定**：回歸集**不要常改**（否則失去「可比」意義）；要改就**版本化**。

> **心智模型**：回歸集＝**你的「真值基準」（ground truth 的近似）**。
> 案例越貼近**真實用戶會問的**（含刁鑽的），它越能反映「上線後好不好用」——**拿線上 log 回頭餵給回歸集是最強的來源**。

---

## 3. 三軸評分（分數 / 成本 / latency）

一個改動要**同時**看三軸——**只看一軸會被誤導**：

| 軸 | 量什麼 | 怎麼算 | 典型陷阱 |
|----|--------|--------|----------|
| **分數（Quality）** | 答案準不準 | 回歸集 `assert` 命中率；RAG 用 recall/faithfulness | 分數升但成本 5 倍 |
| **成本（Cost）** | 花多少錢 | Σ(in+out tokens)×單價＋向量查詢次數 | 分數持平但成本翻倍 |
| **latency（Latency）** | 多快 | p50 / **p95**（不是只看平均） | 平均快但 p95 長尾卡死 |

**A/B 對比範例**（換 prompt 前後）：

| 版本 | 分數（20 案例命中） | 成本/月 | p50 | p95 |
|------|--------------------|---------|-----|-----|
| A（舊 prompt） | 17/20 | US$24 | 1.2s | 3.1s |
| B（新 prompt） | 18/20 | US$19 | 1.1s | 2.8s |

> **心智模型**：**改動要「三軸一起讀」**——分數↑但成本 3 倍＝可能是賠本；分數↓但 latency 大降＝某些場景划算。
> **決策看「每塊錢買到幾分 + 多快」**，不是單看分數。
> **latency 必看 p95**——平均值會把「最壞情況」藏起來，使用者體驗由 p95 決定。

---

## 4. 怎麼打分（自動 + 人核/LLM 評）

| 方法 | 適用 | 優 | 劣 |
|------|------|----|----|
| **規則 assert**（==/in/regex） | 結構化輸出（C1/C3） | 快、可重跑、零成本 | 只測「形式」不測「語意」 |
| **相似度**（embedding 距離） | RAG answer 接近度 | 半自動 | 閾值難調 |
| **LLM-as-judge**（另一模型評） | 開放式 answer 品質 | 能評語意 | 貴、judge 本身也會錯（要固定 judge 模型） |
| **人核** | 高風險/邊界案例 | 最準 | 慢、貴、不能重跑 |

> **心智模型**：**能用自動規則就用規則（可重跑）**；語意的才上 LLM-judge（**固定同一個 judge 模型**才能比）；關鍵邊界留人核。
> 三者**分層**，不要全推給最貴的（人/LLM），成本會被評測本身吃掉。

---

## 5. 線上監控（上線後才看得到的三軸）

回歸集是「**上線前**」；上線後要**持續埋點**：

| 要埋的指標 | 用途 | 告警閾值（例） |
|------------|------|----------------|
| 每次請求 in/out tokens＋總成本 | 成本異常/刷爆 | 單請求成本 > 預算中位數×N |
| latency（p50/p95/p99） | 慢查詢/卡死 | p95 > 3s 持續 5min |
| 錯誤率（4xx/5xx/JSON 解析失敗） | 穩定性 | >2% |
| 工具呼叫失敗率 | Agent 健康 | >5% |
| token/請求 trend（時間序列） | 死循環/回歸 | 突增 3 倍 |

> **心智模型**：**監控＝把「三軸評分」從「lab 一次」變成「線上一直」**。
> **lab 分數**保證「**設計上**好」；**線上監控**保證「**真實流量下**沒退化」——兩者缺任何一個，AI 應用都不可靠。
> **告警要比人察覺快**：設定閾值＋自動通知，而不是「月底看帳單才驚覺」。

---

## 6. 評測反模式（避坑）

1. **只看分數不看成本/latency** → 賠本賺吆喝（三軸要並列）。
2. **回歸集太小（<10）** → 被單例帶偏、過擬合到測試集。
3. **每次改動連測集一起改** → 失去可比性（測集要版本化、穩定）。
4. **只看平均 latency** → p95 長尾被藏起來（要 p50+p95）。
5. **judge 模型跟著換** → A/B 不可比（judge 要固定）。
6. **沒埋線上指標** → 上線後盲飛（回歸集只覆蓋「已知的」，線上才有「未知的」）。

> **心智模型**：評測反模式的根源多是**「只量一軸」或「量一次就放棄」**——
> 正確姿勢＝**多軸並列＋持續跑＋上線後持續監控**。
